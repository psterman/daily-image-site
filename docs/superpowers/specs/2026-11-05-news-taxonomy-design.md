# 见报分类重构：从「平台名」改为「用户思维」

日期：2026-11-05
状态：已批准（用户确认分类集合与往期统一重分）

---

## 1. 背景

见报 tab 顶部第一层筛选（`.chips-tags`）当前有 11 个大类：

```
全部 / 微博 / 科技 / 社区 / 知乎 / 即刻 / 效率 / 博客 / 数码 / 资讯 / AI
```

问题不在于某一个名字不好，而在于**三套分类轴混在同一条 chip 行里**：

| 轴 | 大类 | 用户会怎么理解 |
|---|---|---|
| 平台名 | 微博、知乎、即刻、V2EX | 「这是哪个 App 的内容」 |
| 内容领域 | 科技、效率、数码、AI | 「这是关于什么的」 |
| 内容形态 | 社区、博客、资讯 | 「这是哪种体裁」 |

用户无法建立心智模型 —— 看到「科技」和「微博」并列时，会问「那我到底该怎么找东西」。

## 2. 已批准的决策

| 决策 | 选择 | 理由 |
|---|---|---|
| 分类轴 | **全按内容领域** | 用户思维 = 「我想看什么」 |
| 热榜那 66% | **整体归「热议」一个类**，不按关键词拆 | 拆会误判；平台名由下层真实源名承担 |
| 一条内容能否属于多个领域 | **可以** | 架构已支持；领域天然交叉（AI ⊂ 科技） |
| 往期 11 期 | **统一重分**，不留两套体系 | — |

| **深度阅读** | 阮一峰、博海拾贝、知乎日报 | 6 | 长文，值得存下来慢慢看 |

### 3.1 chip 顺序固定

当前 `build.mjs` 按**条数降序**输出分类列表。必须改成**按 taxonomy 里的固定顺序**。

理由：按条数排会导致「AI」今天在第 3 位、明天 8 条变第 2 位、明天 20 条变第 1 位 —— chip 位置天天乱跳，用户肌肉记忆作废。

固定顺序即上表顺序（热议 → 科技数码 → AI → 效率工具 → 技术社区 → 深度阅读）。

### 3.2 只显示有内容的分类

某天「深度阅读」0 条 → 该 chip 不出现（沿用现有行为：分类列表由实际内容算出）。

### 3.3 下层不变

第二层仍是**真实源名**（微博热搜 / 知乎热榜 / 虎扑步行街 / 驱动之家…），带条数与「来源」标注。

两层分工：**上层按「我想看什么」，下层按「谁说的」**。想按平台精确挑依然可以。

## 4. 新的唯一真相源：`tools/news-taxonomy.json`

分类配置现在散在两处（`rss.config.json` 的 `feeds[].tag`、`daily_headlines.py` 的 `SOURCES` category），必须合并到一处。

```json
{
  "_doc": "见报分类的唯一真相源。改这里 = 改分类，不用动任何代码。",

  "categories": [
    { "key": "hot",   "label": "热议" },
    { "key": "tech",  "label": "科技数码" },
    { "key": "ai",    "label": "AI" },
    { "key": "tools", "label": "效率工具" },
    { "key": "dev",   "label": "技术社区" },
    { "key": "deep",  "label": "深度阅读" }
  ],

  "sourceCategory": {
    "微博热搜": "hot",
    "知乎热榜": "hot",
    "虎扑步行街": "hot",
    "抽屉热榜": "hot",
    "驱动之家": "tech",
    "爱范儿": "tech",
    "AIHOT精选": "ai",
    "即刻·AI编程": "ai",
    "少数派": "tools",
    "少数派发现": "tools",
    "V2EX 热榜": "dev",
    "V2EX创意": "dev",
    "即刻·行业内幕": "dev",
    "阮一峰": "deep",
    "博海拾贝": "deep",
    "知乎日报": "deep"
  },

  "keywordTags": [
    {
      "tag": "ai",
      "words": ["AI", "人工智能", "大模型", "GPT", "ChatGPT", "Claude",
                "英伟达", "算力", "智能体", "机器学习"]
    }
  ],

  "maxExtraTags": 2
}
```

### 4.1 字段语义

| 字段 | 含义 |
|---|---|
| `categories[].key` | 内部标识，用于 `sourceCategory` / `keywordTags` 引用 |
| `categories[].label` | **显示文本**。manifest 里的 `tag` / `tags[]` 存 label（保持现有格式，前端零改动） |
| `sourceCategory` | 源名 → 主分类 key。**每个源必须有**，没有则构建失败 |
| `keywordTags[].tag` | 关键词命中后追加的分类 key |
| `keywordTags[].words` | 匹配词，大小写不敏感 |
| `maxExtraTags` | 一条内容最多追加几个关键词分类（防关键词堆叠导致分类膨胀） |

### 4.2 归属计算规则

```
tags(item) = [主分类] + 关键词命中的分类（去重、排除主分类、截断到 maxExtraTags）
tag(item)  = 主分类（显示在条目徽章上）
```

关键词匹配范围：**标题 + 摘要**。

匹配规则：
- 大小写不敏感（`AI` / `ai` / `Ai` 都算）
- 中文词直接子串匹配
- 英文词按**单词边界**匹配（`ai` 不应命中 `said`；但 `GPT-4` 应命中 `GPT`）
- 关键词表**保守**：只放明确词。宽词（如 `App`、`系统`）不放 —— 微博热搜里一条「特朗普会见某 App 开发者」会误命中

## 5. 代码改动

### 5.1 `tools/news-taxonomy.json`（新建）

见 §4。

### 5.2 `tools/build.mjs`（核心改动）

在 `newsItems` 组装完成之后、计算分类列表之前，插入统一重算：

```js
// 现状（约 793-860 行）：RSS items 带 tag/tags:[it.tag]，
// 头条 items 直接 push 进来，分类列表按条数降序。
// 改后：统一用 taxonomy 重算，主分类来自 sourceCategory[source]，
// 附加分类来自关键词命中；分类列表按 taxonomy 固定顺序输出。
```

具体：
1. 读 `tools/news-taxonomy.json`（构建失败则报错中止，不静默用默认值）
2. 遍历 `newsItems`：
   - 主分类 = `taxonomy.sourceCategory[item.source]`
     - **源未映射 → 构建失败**（附源名和已映射源列表）。不允许 fallback 到「其它」——
       悄悄归到「其它」会让用户以为分类没问题，实际是新源漏配了。
   - 关键词命中 → 追加分类（去重、排除主分类、截断 `maxExtraTags`）
   - `item.tag` = 主分类 label；`item.tags` = 全部归属的 label 数组
3. 分类列表 = 按 `taxonomy.categories` 顺序，**只保留当天有内容的**
4. `manifest.tabs[news].tags` = 该有序列表

### 5.3 `tools/rss.config.json`

删除每个 feed 的 `tag` 字段 —— 分类改由 taxonomy 统一管。

`fetch-rss.mjs` 里 `tag: r.feed.tag || r.feed.name || ''` 会退化为用源名当 tag，但 §5.2 会整体覆盖，**不影响结果**。保留这行作为容错（防止有人单独跑 `fetch-rss.mjs` 时拿到 undefined）。

同时更新该文件 `_doc` 里「tag=归类标签（顶部的标签 chips 就是按它分组）」这句 —— 已不成立，分类改由 `news-taxonomy.json` 管。

### 5.4 `tools/grab/daily_headlines.py` —— **不改**

`SOURCES` 的第三个参数（category）保持现状（`知乎` / `微博` / `V2EX` / `科技` / `社区`）。

理由：
- **分类决策只发生在 build.mjs 一处**，一律以 `taxonomy.sourceCategory[item.source]` 为准。
  Python 侧写的 category 字段**不再参与分类决策**，只作为归档线索保留（`headlines.json` 格式不变，归档页重建和排查不受影响）。
- 反过来，如果把 Python 侧也改成 taxonomy key，就等于**又造出第二处需要跟 taxonomy 同步的配置** ——
  忘了同步时两处不一致，而构建只用其中一处，排查起来很费劲。
  一处真相源 > 两处「看起来一致」的配置。
- `tools/headlines.mjs` 的 `SOURCE_CATEGORY` 兜底表保留（旧日期 JSON 没有 category 时要用）。

**「源未映射 → 构建失败」这条闸门，正是用来兜住漏配的新源**：Python 侧加了新源但 taxonomy 没配，构建直接报错并列出已映射的源。

### 5.5 `site/app.js` —— **不改**

前端已经天然支持多归属，一行都不用改：

| 位置 | 现状 | 是否要改 |
|---|---|---|
| `li.setAttribute('data-tags', it.tags.join(' '))` | 数组，空格分隔 | 否 —— 已支持多归属 |
| `applyFilter()` 的 `ts.indexOf(curTag) >= 0` | 包含匹配 | 否 —— 多归属下任一大类都能命中 |
| 徽章 `tg.textContent = it.tag` | 显示单个 `it.tag` | 否 —— `it.tag` 就是主分类，天然只显示一个 |
| 上层 chip `for (i in tags) mkTag(tags[i], tags[i])` | 按 manifest 数组顺序渲染 | 否 —— manifest 顺序即显示顺序，改 build.mjs 即可固定顺序 |

唯一要确认的是：`it.tag` 必须是**主分类**（不是多分类数组），由 §5.2 保证。

### 5.6 `tools/build.mjs` 新增 `--retag`（往期重分类专用）

| 模式 | 内容 | 图片 | RSS/头条 |
|---|---|---|---|
| 普通构建 | 重新抓 | 重新转码 | 重新抓 |
| `--keep-manifest` | 原样沿用 | 沿用 | 不抓 |
| **`--retag`**（新） | **items 原样沿用，只重算分类标签** | 沿用 | 不抓 |

`--retag` 流程：
1. 读已发布 manifest（`published/<日期>/manifest.<hash>.js`）
2. 取 news tab 的 items，**逐条原样保留**（title / link / source / time / ts / desc）
3. 用新 taxonomy 重算每条的 `tag` / `tags`，重算分类列表
4. 图片 tab 的 items 原样沿用
5. 输出新 manifest（内容哈希变 → 文件名变 → 页面引用跟着变，由 build 生成 index.html）

**闸门**：
- `--retag` 隐含「不重转码」（等价于 `--no-convert`）；同时传 `--no-convert` 也接受。
- 目标日期没有已发布 manifest → **拒绝执行**（不猜、不静默退化成普通构建）。
- `--retag` 与 `--keep-manifest` **互斥**：一个要重算分类，一个要原样沿用。同时传则报错。

## 6. 往期 11 期重分类流程

期次：10-25 / 10-26 / 10-27 / 10-28 / 10-29 / 10-30 / 10-31 / 11-01 / 11-02 / 11-03 / 11-04
（11-05 是当期，内容本身已定，走普通流程即可）

步骤：

1. 写 `tools/news-taxonomy.json`
2. 逐期执行 `node tools/build.mjs --date <日期> --no-convert --retag`
   - **最新一期（11-05）放最后** —— 根路径 `published/index.html` 永远指向最后构建的那一期
3. 逐期验证：
   - manifest 的 news items **逐条内容不变**（title/link/source/time/desc 与已发布版本一致）
   - 只有 `tag` / `tags` / 分类列表变了
   - 图片 items 逐条不变（thumb/full 路径与尺寸）
4. 部署：`publish.ps1 -Date <日期> -SkipBuild -SkipUpload`（图片未变，不必重传 R2）
5. 线上验证：11 个日期页 chip 行都不再出现平台名

**成本与代价（已知）**：
- 11 期 manifest 文件名全变 → 11 个日期页要重新部署
- 边缘缓存最长 24 小时 → 部署后短期内老页面可能仍显示旧分类
- 图片不重传 R2（manifest 图片部分字节不变，R2 键也不变）

## 9. 风险与边界

| 风险 | 处置 |
|---|---|
| 关键词误判（宽词命中无关标题） | 关键词表保守；单元测试锁住单词边界匹配 |
| 新增源忘了配 taxonomy | **构建失败**并列出已映射源 —— 不静默 fallback |
| 分类表改了但忘改某期 manifest | `--retag` 是显式操作，逐期执行逐期验证 |
| 往期重建后边缘缓存仍显示旧分类 | 已知代价，最长 24 小时自然过期 |
| 分类名将来想改 | 改 taxonomy 的 label 即可；但改 label 会改 manifest 字节 → 需重跑 `--retag` |
| 分类数量膨胀 | `maxExtraTags` 限制附加分类数；`categories` 固定 6 个 |
